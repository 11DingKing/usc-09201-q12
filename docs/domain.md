# 林产品批次履历领域约定

项目面向集体林权改革与林下产业协作场景，业务记录需要区分来源、发生时间与当前有效版本。涉及个人、机构或敏感地点的信息只应向职责范围内的角色开放，所有对外结果都应能够追溯到采用的数据版本。

## 事件与状态

- 系统状态完全由只追加事件流推导，事件类型见 `src/domain/events.mjs`：用户与林地登记、标准发布、采收、检验、分级、合批、拆包、交付、重编号、跨仓转移、扫码、锁定、部分报废、整批处置、管控单、通知。
- 任何修正（迟到检验、重编号、报废、转移、重复扫码）都以**追加新事件**表达，不提供修改或删除既有事件的能力。
- 每条事件携带单调 `seq`、`occurredAt`（业务发生时间，非记账墙钟）、操作人与前序事件哈希，形成可审计哈希链。
- 读模型由事件重放得到，可按 `asOfTime`/`asOfSeq` 重建任意历史时点，回答“当时标准”“当时库存”。

## 批次与血缘

- 内部批次标识永不改变；对外批次号按类型单调递增且不复用，重编号只新增别名。
- 合批（多对一）与拆包（一对多）以带数量的有向边记录；正反向追溯沿边遍历。
- 混合成品的来源集合为其全部上游采收批，可对应多块林地、多户林农。
- 失效影响沿下游边展开：仅仍有在库余量的批次进入锁定候选，已交付批次生成逐客户的下游通知，不含该物料的批次（如干净的合批输入）不在影响面。

## 标准版本

- 标准按产品发布多个版本并带生效时间；检验默认采用**检验发生时刻已生效**的版本，记录中固化版本号，追溯可回到采收当时标准。

## 角色与可见性

- `enterprise`（质量负责人/加工企业）：登记林地与标准、记录检验与全部流转、执行管控与账本审计。
- `supplier`（林农）：可为自家林地登记采收、扫描相关批次；只能看到与自身相关的批次、处置与通知，其他林农身份、地块位置、下游客户信息一律脱敏，且看不到与己无关的通知收件人。
- API 密钥以哈希存储，注册时仅返回一次明文。
